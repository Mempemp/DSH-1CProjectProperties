# 1С в этом проекте: как работать агенту

Проект — исходники конфигурации 1С: выгрузка в XML-файлы или каталог EDT.
Истина о коде и метаданных лежит в файлах проекта; платформа, база и данные —
снаружи, за параметрами проекта.

Человек смотрит результат в панели приложения «1С»: дерево метаданных, diff, git,
ход выгрузки и подключение к базе. Панель — место, куда смотрит человек; агент
правит файлы инструментами и проверяет их сам.

## Что установлено

| Группа | Что это | Чем зову |
|---|---|---|
| Код 1С | MCP `rlm`: индекс по выгрузке (модули, объекты, вызовы, макеты) | `rlm_start` → `rlm_execute`; хелперы `find_module`, `find_by_type`, `get_object_full_structure`, `safe_grep`, `git_search` |
| Платформа | MCP `1c-platform-context`: справка платформы и валидатор BSL (локальный сервер, поднимает плагин) | `search`, `info`, `get_members`, `get_constructors`, `validate_module` |
| Стандарты | MCP `v8std`: публичный сервер знаний по платформе и БСП | `v8std_search`, `v8std_get_page`, `v8std_get_related`, `v8std_explain_snippet`, `v8std_explain_diagnostics` |
| Стандарты ИТС | MCP `1c-naparnik`: Напарник — ответы по стандартам, БСП и методичкам словами (движок bsl-analyzer, профиль reference; плагин подключает его сам, когда задан токен) | `its_help` |
| Файлы | нативные | `read`, `write`, `edit`, `glob`, `grep` |
| Оболочка | нативные | `pwsh` (Windows), `bash` |
| Оркестрация | нативные | `skill`, `subagent`, `todo_write`, `web_search`, `read_page` |

Параметры проекта (база, пользователь, платформа, каталог выгрузки) — в
`.dsh/1c-project.json`, файл правит плагин. У набора comol свой файл параметров —
`.dev.env`. Значения берутся оттуда, а не из памяти и не из догадок.

## Задача → плейбук

| Задача | Файл |
|---|---|
| Найти модуль, объект, вызов процедуры, макет, общий модуль | `.dsh/rules-own/find.md` |
| Проверить метод, тип, конструктор, значение перечисления, стандарт | `.dsh/rules-own/platform.md` |
| Вопрос «как правильно», «почему правило», выбор метода БСП, разбор типовой | `.dsh/rules-own/its.md` |
| Пишу или правлю код 1С: BSL, запросы, модули, расширения | `.dsh/rules-own/code.md` |
| Прочитать и поправить модуль `.bsl` | `.dsh/rules-own/edit.md` |
| Менять метаданные: реквизиты, ТЧ, перечисления, роли, макеты | `.dsh/rules-own/metadata.md` |
| База: подключение, выгрузка, загрузка, обновление конфигурации БД | `.dsh/rules-own/db.md` |
| Формы, элементы формы, командный интерфейс | `.dsh/rules-own/ui.md` |
| Ревью задачи, плана или изменённого кода | `.dsh/rules-own/review.md` |

Плейбук читается до работы, а не после: в нём точные имена, аргументы и порядок
шагов. Задача не попадает ни в одну строку таблицы — работаю по этому файлу и
`platform.md`; новых инструментов не изобретаю.

## Жёсткие правила

1. **API платформы проверяю до кода.** Метод, свойство, конструктор, значение
   перечисления, число аргументов — сначала `platform.md` (`info`, `get_members`,
   `get_constructors`, `validate_method_call`), потом текст модуля. Память и
   аналогия с соседними версиями платформы доказательством не считаются.
2. **После правки модуля — `validate_module`.** Правка без проверки не считается
   сделанной: находки `high` устраняются, `low` проверяются и объясняются. Если в
   ответе `symbols_available: false`, сказать прямо, что имена конфигурации не
   проверялись.
3. **XML метаданных руками не правлю, если в наборе есть навык.** Сначала ищу
   навык под этот вид объекта (`glob` по `.dsh/skills/**/SKILL.md`, затем
   `skill`); ручная правка XML — только когда навыка нет, по образцу соседнего
   объекта того же вида и с предупреждением в ответе.
4. **Значения не выдумываю.** Путь к базе, пользователь, версия платформы,
   каталог выгрузки — из `.dsh/1c-project.json` (и файла набора, если он есть).
   Пусто — значит пусто: спрашиваю человека, а не подставляю правдоподобное.
5. **Чего нет в сборке — не ищу.** Список MCP-серверов и нативных инструментов
   выше полный. Инструмент не отвечает — ухожу в резервную ветку своего плейбука
   («Если недоступно») и говорю об этом; молчаливое «сделаю как получится»
   запрещено.
6. **Ответ `its_help` — не доказательство.** Ссылки на стандарт в нём может не
   быть, формулировки общие. Имена методов, типы и значения проверяю по
   `platform.md`, существование объектов — по `rlm` (`safe_grep`,
   `get_object_full_structure`). В ответе человеку называю, что проверил и чем.
   Ответ без сверки в код не идёт.

## Файлы правил

- `USER-RULES.md` — правила владельца проекта. DSH не загружает его сам, поэтому
  читаю в начале работы вместе с этим файлом. Свои правила человек пишет здесь:
  `AGENTS.md` управляемый, правки в нём теряются.
- `memory.md` — память проекта, если он есть: устойчивые факты и принятые
  решения. Читаю перед работой, дописываю короткой записью, когда решение не
  выводится из кода.
- `.dsh/rules-own/environment.md` — что где лежит в этом проекте, какие MCP
  реально настроены. Файл генерирует плагин, править его не нужно.
- `.dsh/rules-own/*.md` — плейбуки; плагин перезаписывает их при обновлении.

`AGENTS.md` собирает плагин «1С: Параметры проектов»: шапка — эта, ниже — блок comol, если он включён. Правки в `AGENTS.md` теряются при обновлении правил.
