# 0.15.11

## MCP-менеджер: работа на ядре 0.2.2-rc.3 и совместимость с прежними сборками

Сервис `ctx.mcpManager` в ядре rc.3 принимает сервер через `register(name, entry)`
и снимает его возвращаемым disposer'ом; состояний — `list()`, перезапуск —
`restart()`. Методов `registerServer`, `unregisterServer`, `getStatus`,
`reconnect` в этой линии нет.

Плагин выбирает форму по факту наличия метода:

- есть `register` — три сервера (`1c-platform-context`, `1c-bsl-checks`,
  `1c-naparnik`) регистрируются через него, снятие идёт disposer'ом;
- есть только `registerServer` — работает прежняя ветка, включая поле
  `existing` для записи, добавленной в менеджере вручную;
- состояние читается из `list()`, перезапуск — через `restart()`, они же
  используются для проверки «сервер отвалился за время сборки индекса».

Отказ менеджера больше не вылетает текстом исключения в карточку: занятое имя
называется словами («сервер уже настроен в менеджере вручную»), прочие причины
попадают в поле `managerError` карточки «Платформенный контекст (MCP)».

## Параметры проекта: подтверждение сохранения

Плашка сохранения — «Готово» с галочкой, как у тостов приложения. Галочка стоит
и у остальных успешных операций окна. Из группы «1С:Напарник» убрана поясняющая
строка про `its_help`.

## Индекс кода: возраст после обновления

Карточка индекса считает возраст по более свежей из двух меток — `built_at`
внутри индекса и время последней успешной сверки, которое ведёт плагин.
Индекс, у которого метка сборки не сдвинулась, но сверка прошла, показывается
актуальным и получает пояснение с датой сверки; честная старость (сверка тоже
старше `RLM_INDEX_MAX_AGE_DAYS`) остаётся «устарел по возрасту».

Командная строка индексации ищется в порядке: `bin` плагина, `~/.local/bin`,
затем `PATH`. Сборка CLI старше 1.46 при `index update` не сдвигает метку
сборки, поэтому её появление впереди нашего окружения давало бесконечное
«устарел по возрасту» при формально успешном обновлении.
